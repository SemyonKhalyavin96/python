# План подготовки к архитектурной секции интервью

## Цель
Научиться проектировать рациональное работающее хранилище данных под конкретный бизнес-кейс, демонстрируя аналитическое мышление, знание моделей данных, технологического стека и аспектов эксплуатации.  
**Ключевой принцип:** не просто дать ответ, а провести интервьюера через логику ваших решений. 70% времени — практика, 30% — теория.

---

## Общая схема подготовки (9 дней)

| День | Тема | Формат |
|------|------|--------|
| 1 | Фундамент: требования, метрики качества, архитектурные стили | Теория + конспект |
| 2 | Модели данных и DWH (звезда, снежинка, SCD, Data Vault, Lakehouse) | Теория + схемы |
| 3 | Технологический стек: хранение, обработка, оркестрация | Сравнение таблицей |

| 9 | Легкое повторение, отдых, подготовка ссылок/рисовалок | Релакс + чеклист |

## 1. Сбор требований (первые 5–10 минут интервью)

### Функциональные требования (ФТ) — примеры вопросов
- Какие отчёты нужны? (конверсия по каналам, воронка событий, когортный анализ)
- Детализация (день, час, событие)?
- Период хранения данных?
- Фильтры и срезы?
- Кто пользователи (число, роли, BI-инструменты)?
- Источники данных (API, логи, реляционные БД, файлы)?
- Частота обновления отчётов?

### Нефункциональные требования (НФТ) — примеры вопросов
- SLA по времени ответа: 5 секунд, 1 час?
- Объёмы данных: 10 ГБ/день, 10 ТБ/день?
- Доступность: 99.9% или 99.99%?
- Согласованность: сильная или конечная?
- Бюджет (hard limit)?
- Geo-распределение, требования к безопасности (PII, шифрование)?

> **Материалы:** статья «Non-functional requirements for data platforms» (Medium), CAP, PACELC.

## 2. Модели данных и архитектуры хранилищ

| Модель | Когда использовать | Плюсы / минусы |
|--------|-------------------|----------------|
| **Звезда (Kimball)** | Классические витрины для отчётов и BI | + простота, скорость агрегаций<br>- избыточность при изменении измерений |
| **Снежинка** | Нормализованные измерения (редко) | + экономия места<br>- сложнее запросы |
| **Data Vault 2.0** | Много источников, нужна историчность и гибкость | + масштабируемость, аудит<br>- сложность, больше JOIN |
| **Data Lakehouse** | Единое хранилище для сырых и обработанных данных (Iceberg, Delta) | + ACID, time travel, schema evolution |

**Что обязательно уметь:**
- Нарисовать схему «звезда» для маркетинговой аналитики: факт (событие/покупка), измерения (пользователь, канал, время, товар).
- Обосновать гранулярность (например, факт = каждая строка события лога).
- Объяснить SCD Type 2 (для измерения «пользователь»: город, статус, сегмент).

> **Материалы:** «The Data Warehouse Toolkit» (Kimball), главы 1-4; статья про Data Lakehouse на Databricks.

---

## 3. Технологический стек (с чем аргументировать выбор)

### Хранение сырых данных
| Технология | Плюсы | Минусы |
|------------|-------|--------|
| S3 + Iceberg / Delta Lake | ACID, time travel, schema evolution, дёшево | Требует движка для чтения/записи |
| HDFS | Стабильность | Устаревает, дорогое администрирование |

### Движки для витрин / аналитики
| Технология | Сценарий |
|------------|----------|
| ClickHouse | Сверхбыстрые агрегаты, real-time, большие объёмы |
| Greenplum / Redshift | Классические MPP DWH |
| BigQuery | Serverless, ad-hoc |
| PostgreSQL | Малые объёмы (<1 ТБ), простые отчёты |

### Обработка данных (ETL/ELT)
- **Spark** – универсальный, тяжеловесный (batch, микробатч).
- **Flink** – стриминг, exactly-once, события в реальном времени.
- **dbt** – если всё хранится в DWH, трансформации SQL (ELT).
- **Airflow** – оркестрация батчей.

### Как аргументировать (пример)
> *«Для B2C маркетинга – сотни миллионов событий в день. Нужны гибкие срезы по времени и каналам. Я выберу S3 + Iceberg как сырой слой (дёшево, ACID) и ClickHouse для витрин (агрегаты за секунды). ETL на Spark – потому что данные приходят в разных форматах (JSON, Avro), требуют сложной очистки».*

---

## 4. Потоки данных и обработка

| Архитектура | Описание | Плюсы | Минусы |
|-------------|----------|-------|--------|
| **Batch** | Периодический запуск (раз в час, день) | Простой, дешёвый | Нет real-time |
| **Streaming** | Непрерывная обработка (Kafka+Flink) | Минимальная задержка | Сложнее гарантии |
| **Lambda** | Batch + speed layer, потом слияние | Надёжно | Сложность поддержки |
| **Kappa** | Всё через стриминг, batch = повтор | Современнее, проще | Требует мощного стриминга |

**Что нужно показать:**
- Источники → Kafka → Spark Streaming → S3/Iceberg (сырые события)
- Построение витрин: триггер по расписанию (Airflow) или материализованные представления в ClickHouse
- Обработка поздних данных: watermark, upsert в Iceberg (MERGE)

---

## 5. Аспекты эксплуатации

- **Отказоустойчивость:** репликация в S3 (11 девяток), checkpoint в Spark/Flink, перезапуск джобов.
- **Мониторинг и алертинг:** Prometheus + Grafana, логи (ELK).
- **Производительность:** партицирование (по дате), Z-order / сортировка в Iceberg, правильный ключ партиции в ClickHouse.
- **Безопасность:** шифрование в S3 (SSE-S3/KMS), IAM-политики, маскирование PII.
- **Управление затратами:** автоотключение кластеров, Spot-инстансы, tiered storage (горячие/холодные данные).

## 6. Шаблон ответа на кейс (структура, которую оценят)

1. **Уточнить требования** (5–10 мин) – задать 5–10 вопросов по ФТ и НФТ.
2. **Сформулировать ограничения и метрики успеха** (2 мин) – прописать вслух.
3. **Высокоуровневая архитектура** (10 мин) – нарисовать блоки:  
   *Источники → Ingestion (Kafka) → Raw storage (S3+Iceberg) → Processing (Spark) → Mart storage (ClickHouse) → Serving (API/BI)*
4. **Модель данных** (10 мин) – схема фактов и измерений, обоснование гранулярности.
5. **Детали ключевых компонентов** (10 мин) – дедупликация, обновление SCD, партиционирование.
6. **Оценка ресурсов и cost** (5 мин) – объём данных, vCPU, стоимость S3.
7. **Риски и альтернативы** (5 мин) – «Если данных станет в 100 раз больше, мы можем перейти от Spark к Flink или использовать материализованные представления в ClickHouse».

## 7. Пример кейса: маркетинговая аналитика B2C

### Исходные данные
- **Источники:** события из приложения (user_id, action, timestamp, product_id, channel), CRM (user_id, регион, статус), рекламные системы (cost, campaign_id).
- **Требования:** отчёт «конверсия по каналам за день» + витрина «воронка событий в реальном времени».

### Предлагаемое решение
- **Raw:** S3 + Iceberg (слои bronze, silver, gold).
- **Processing:** Spark Structured Streaming для real-time воронки (обновлять каждые 5 минут), batch Spark ночью для агрегатов по дням.
- **Витрины:** ClickHouse – таблицы фактов с партицией по дате, ORDER BY (channel, event_time).
- **Модель:** звезда: факт «событие» (session_id, user_id, event_type, timestamp), измерения – пользователь (SCD2), канал, время, продукт.
- **Обоснование:** ClickHouse даёт дешёвые агрегаты, Iceberg позволяет безопасно менять схему (например, добавить поле `app_version` без переписывания данных).

## 10. Чего делать не стоит

- ❌ Не начинайте сразу рисовать. Потратьте первые 5-10 минут на сбор требований.
- ❌ Не предлагайте «идеальное» решение в вакууме. Решение должно быть рациональным и привязанным к кейсу. Всегда упоминайте компромиссы (trade-offs).
- ❌ Не игнорируйте нефункциональные требования — это дополнительные баллы.
- ❌ Не бойтесь сказать «Я не знаю». Честно скажите и предложите альтернативу на основе ваших знаний.
